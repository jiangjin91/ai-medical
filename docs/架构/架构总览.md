# 架构总览

<!-- 本文作用：描述患者端医疗服务智能客服的整体架构，以及现有电商客服项目迁移到医疗场景后的模块关系。 -->

## 当前 MD 的作用

本文件用于回答“系统整体怎么组成、每一层负责什么、迁移时哪些模块可以复用”。它是技术方案入口，不写具体接口字段，也不写单个页面细节。

## 目标架构

```text
患者端 Web/App/H5
        |
        v
ai-frontend
患者首页 / 对话助手 / 任务卡 / 人工转接入口
        |
        v
ai-service
意图识别 / 任务规划 / 多轮状态机 / 知识问答 / 风险拦截
        |
        v
backend-service 或医院业务网关
预约挂号 / 检查检验 / 报告查询 / 缴费 / 消息通知 / 人工客服
        |
        v
医院系统
HIS / LIS / PACS / EMR / 支付平台 / 互联网医院 / 工单系统
```

## 模块职责

| 模块 | 当前项目位置 | 医疗化后的职责 |
| --- | --- | --- |
| 患者端前端 | `ai-frontend` | 展示患者待办、对话、服务卡片、人工转接状态 |
| AI 编排服务 | `ai-service` | 将患者表达转成任务，控制多轮流程和安全边界 |
| 业务服务 | `backend-service` | 当前是电商模拟后端，后续应替换为医疗业务适配层 |
| 知识库配置 | `ai-service/atguigu/config`、`flow_config` | 承载医院审核过的流程知识、FAQ、任务规则 |
| 外部系统适配 | 待新增 | 对接 HIS、LIS、PACS、互联网医院和工单系统 |

## 迁移原则

1. 保留多轮对话、任务状态机、知识问答、人工转接这些主体能力。
2. 将“订单、物流、退款、商品”等电商对象替换为“预约、检查、报告、缴费、复诊、转接”。
3. 医疗规则必须可审核、可追溯，不能只依赖大模型自由生成。
4. 优先落地患者服务流程，不做自动诊断、自动处方和治疗决策。
